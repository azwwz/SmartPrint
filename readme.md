# SmartPrint：从虚拟打印机到智能打印管理，自己开发一套手动双面打印管理软件

## 一、项目缘起：为什么要开发 SmartPrint？

家里有一台 HP LaserJet 1020 激光打印机。

平时打印 Word 文档、PDF、网页资料都没有问题，但打印大量学习资料时，手动双面打印一直是一件比较麻烦的事情。

HP LaserJet 1020 本身不支持自动双面打印。如果需要双面打印，只能先打印一面，再把纸张重新放回进纸托盘，打印另一面。

看起来只是多操作一步，实际使用时却有不少问题：

1. 每次都需要自己计算奇数页和偶数页。
2. 打印量比较大时，需要分批打印，否则翻面和重新进纸都比较麻烦。
3. 如果打印过程中发生卡纸，很难准确判断哪些纸张已经完整打印。
4. 如果打印任务中途出现异常，通常只能取消任务、重新打印，容易造成重复打印或者漏页。
5. Word、PDF 阅读器和浏览器的打印界面各不相同，打印设置也不统一。
6. 打印任务一旦中断，用户还需要自己记住当前打印到了哪一页、哪一批。

我真正想解决的，并不是简单的奇偶页拆分，而是整个手动双面打印过程的管理问题。

因此，我准备开发一个 Windows 桌面软件：**SmartPrint**。

它不打算重新开发打印机驱动，也不打算直接控制打印机内部的机械结构，而是通过虚拟 PDF 打印机接收打印任务，再由自己的程序负责文档管理、页面处理、分批打印、翻面提示、打印确认和异常恢复。

最终希望实现这样的效果：

无论是在 Word、PDF 阅读器还是浏览器中，只要按下 `Ctrl + P`，选择 PDF24 虚拟打印机，就可以进入统一的打印管理流程。

## 二、项目最终目标

SmartPrint 不是一个普通的 PDF 打印工具，而是一个围绕手动双面打印设计的任务管理软件。

第一版主要解决六件事：

- 统一接收来自不同 Windows 软件的打印任务。
- 自动管理 PDF 文档和打印任务。
- 自动计算正反面页码，并按照物理纸张分批。
- 每次只打印一个页面，等待用户确认后再继续。
- 出现卡纸、污损、断电等异常时，能够暂停、记录并正确补打。
- 手动双面打印时，每批反面按物理纸张编号降序提交，与翻面后纸堆的实际堆叠顺序一致。

### 2.1 统一打印入口

不希望为 Word、浏览器、PDF 阅读器分别开发不同的处理逻辑。

用户只需要在 Windows 打印窗口中选择 PDF24 虚拟打印机。

打印任务会自动转换为 PDF 文件，并保存到 SmartPrint 的待处理目录。

整体流程如下：

```text
Word / PDF / 浏览器 / 其他软件
                |
                v
          Windows 打印窗口
                |
                v
          PDF24 虚拟打印机
                |
                v
          自动生成 PDF
                |
                v
       SmartPrint 自动接收
                |
                v
          打印任务管理
                |
                v
          PDF 预览与设置
                |
                v
          页面与纸张管理
                |
                v
          逐面提交打印
                |
                v
          用户确认实际出纸
                |
                v
          翻面 / 下一张纸
                |
                v
          异常处理与补打
                |
                v
             任务完成
```

这里有一个重要的设计原则：

**SmartPrint 不接管 Windows 的整个打印系统，而是通过成熟的虚拟 PDF 打印机接收文档。**

这样可以避免自己编写 Windows 打印驱动所带来的复杂性，把开发重点放在打印任务管理和异常恢复上。

### 2.2 统一管理打印任务

所有进入 SmartPrint 的 PDF 都应该成为一个独立的打印任务。

任务管理界面需要显示：

- 任务编号。
- 文件名称。
- 文档页数。
- 纸张大小和方向。
- 创建时间。
- 当前打印状态。
- 当前打印进度。
- 预计使用纸张数量。
- 预计需要打印的批次数。

任务状态需要能够反映实际流程，而不只是简单的“正在打印”和“打印完成”。

目前规划的主要状态包括：

| 状态 | 含义 |
|---|---|
| 待处理 | PDF 已接收，尚未确认打印 |
| 已准备 | 用户已经确认打印参数 |
| 打印正面 | 正在执行正面打印流程 |
| 等待翻面 | 当前批次正面已完成，等待用户整理和翻面 |
| 打印背面 | 正在执行反面打印流程（按纸张编号降序） |
| 已暂停 | 用户主动暂停任务 |
| 异常待处理 | 打印过程中出现异常，需要用户检查 |
| 待补打 | 存在需要重新打印的物理纸张 |
| 已完成 | 所有纸张均已打印并经用户确认 |
| 已取消 | 用户取消任务 |

任务状态不能只保存在程序运行期间的内存中。

如果 SmartPrint 意外退出，重新打开后，应该能够恢复之前的任务记录和打印进度。

因此，使用 SQLite 保存任务、纸张、打印记录和用户确认信息。

### 2.3 PDF 预览与打印设置

在正式打印之前，应该能够预览 PDF。

第一版至少需要支持：

- 查看页面内容。
- 显示总页数和当前页码。
- 上一页、下一页和指定页跳转。
- 页面缩放。
- 查看页面尺寸。
- 确认打印任务是否正确。

第一版不准备开发复杂的 PDF 编辑功能。

重点是让用户在打印前确认文档，避免错误文件直接进入打印流程。

### 2.4 按照物理纸张分批

SmartPrint 默认每批管理 5 张物理纸。

这里需要特别说明：

**每批默认 5 张纸（设置里可改成 1–20 张），只是纸张管理和翻面管理的单位，不代表一次性提交一整批的页面。**

一张纸通常对应 PDF 中的两个页面。

例如，一份 10 页 PDF：

| 物理纸张 | 正面 | 反面 |
|---|---|---|
| 第 1 张 | 第 1 页 | 第 2 页 |
| 第 2 张 | 第 3 页 | 第 4 页 |
| 第 3 张 | 第 5 页 | 第 6 页 |
| 第 4 张 | 第 7 页 | 第 8 页 |
| 第 5 张 | 第 9 页 | 第 10 页 |

第一批包含 5 张物理纸，正面对应第 1、3、5、7、9 页，反面对应第 2、4、6、8、10 页（反面实际提交顺序见本节末尾的"反面逆序"说明）。

但实际执行时，不会一次性把这 5 个页面全部提交给打印机。

而是按照下面的方式执行：

```text
提交第 1 页
    |
    v
等待用户确认第 1 页完整出纸
    |
    v
提交第 3 页
    |
    v
等待用户确认第 3 页完整出纸
    |
    v
提交第 5 页
    |
    v
等待用户确认第 5 页完整出纸
    |
    v
提交第 7 页
    |
    v
等待用户确认第 7 页完整出纸
    |
    v
提交第 9 页
    |
    v
等待用户确认第 9 页完整出纸
    |
    v
提示用户整理纸张并翻面
```

用户实际检查纸张、整理纸张并确认翻面之后，才开始反面打印。

反面也采用同样的逐页提交和逐页确认方式。

需要特别说明的是反面的**先后顺序**：正面按纸张编号升序打印（第 1、2、3、4、5 张纸），但最后打印的那张纸会落在出纸托盘的**最上方**，翻面放回进纸托盘后它最先进入打印机。因此，每批反面必须按纸张编号**降序**打印——先打第 5 张纸的背面，再逐张向前：

```text
正面：第 1 页 → 第 3 页 → 第 5 页 → 第 7 页 → 第 9 页
翻面确认
反面：第 10 页 → 第 8 页 → 第 6 页 → 第 4 页 → 第 2 页
```

这条规则只改变"先提交哪张纸的背面"，不改变纸张编号与正反面页码的对应关系（第 5 张纸仍然是"正面第 9 页、背面第 10 页"，第 10 页依旧是第 5 张纸的背面），也不是把整个 PDF 的偶数页简单全局倒序：

- 逆序只在本批次内部进行，每批完成后才进入下一批，不能跨批次全局倒序；
- 没有背面内容的纸张（奇数页 PDF 的最后一张纸）直接从反面顺序中跳过，不会生成空白背面；
- 作废的异常纸张从当前循环中排除，剩余纸张仍然按编号降序打印。

这与"本批所有纸张叠成一摞、统一翻面"的放纸方式相对应；如果以后的打印机或翻面方式不同，才需要考虑把反面顺序做成可选项。详细的修改背景与验收计划见 [`SmartPrint_反面打印逆序开发文档.md`](SmartPrint_反面打印逆序开发文档.md)。

## 三、核心设计原则：逐面提交、逐面确认

这是整个 SmartPrint 最重要的设计原则。

普通打印软件通常只关心打印任务有没有发送成功，或者 Windows 打印队列是否已经处理完成。

但 SmartPrint 需要关心的是：

**每一面纸张是否真的、完整地从打印机中出来了。**

### 3.1 为什么不能依赖 Windows 打印状态？

在开发过程中，我专门测试了 Windows 打印队列和 HP LaserJet 1020 的状态反馈能力。

测试表明，Windows 打印队列能够提供一定的任务信息，但这些信息并不能可靠地代表实际纸张输出情况。

例如：

- Windows 队列中的任务消失，不代表纸张一定完整出纸。
- 队列显示空闲，不代表当前纸张没有卡在打印机内部。
- 系统显示任务完成，不代表没有缺页、污损或者半张纸。
- 打印机出现异常时，系统返回的信息也不能准确指出哪一张纸需要补打。

因此，SmartPrint 不应该根据 Windows 队列状态自动推进打印流程。

系统状态可以用于辅助观察，例如判断打印任务是否还在队列中、打印机是否可能离线，但不能作为纸张完成的最终依据。

**最终是否完成，必须由用户检查实际纸张并手动确认。**

### 3.2 一个页面任务只能有一个未确认项

SmartPrint 必须遵守以下规则：

**任何时候，最多只能存在一个已经提交、但尚未经过用户确认的页面打印任务。**

也就是说：

1. 提交一个 PDF 页面。
2. 等待打印命令返回和相关状态信息。
3. 等待用户检查实际纸张。
4. 用户确认这一面完整出纸。
5. 软件记录确认结果。
6. 只有确认完成后，才允许提交下一个页面。

如果用户没有确认，软件就不能继续提交下一页。

即使 Windows 打印队列已经显示空闲，也不能跳过用户确认。

如果用户点击暂停、程序意外退出或者打印机发生异常，当前未确认页面必须保留为待核对状态，不能直接当作成功，也不能在恢复时自动重复发送。

### 3.3 明确区分三个概念

SmartPrint 必须区分：

| 概念 | 含义 |
|---|---|
| 打印命令已发送 | SmartPrint 已经调用打印程序 |
| Windows 队列已处理 | Windows 打印系统已经处理了相关任务 |
| 用户确认完整出纸 | 用户实际检查纸张后确认这一面打印正常 |

这三个概念不能混为一谈。

其中，只有第三项才能真正推进 SmartPrint 的打印流程。

## 四、技术方案：为什么选择这些工具？

SmartPrint 是一个 Windows 桌面应用。

开发过程中，希望尽可能使用成熟组件，把精力放在真正需要自己实现的打印管理逻辑上。

目前采用的技术方案如下：

| 技术 | 用途 |
|---|---|
| Python | 主要开发语言 |
| PySide6 | Windows 桌面界面 |
| PDF24 Creator | 虚拟 PDF 打印机和自动保存 |
| PyMuPDF | PDF 文件读取、页面信息和处理 |
| SumatraPDF | 调用 Windows 打印系统打印指定页面 |
| SQLite | 保存任务、纸张和打印记录 |
| watchdog | 监控 PDF 接收目录 |
| PyInstaller | 最终打包成 Windows 应用 |

### 4.1 PDF24 Creator：负责接收打印任务

PDF24 是 SmartPrint 的统一打印入口。

主要作用：

1. 接收 Windows 应用发来的打印任务。
2. 将打印内容转换为 PDF。
3. 自动保存 PDF 文件。
4. 将文件放入 SmartPrint 的待处理目录。

目前已经完成 PDF24 的基本配置和实际测试。

保存目录：

```text
D:\dev\SmartPrint\Data\incoming
```

文件名模板：

```text
%Y-%m-%d_%H-%M-%S_$id_$fileName
```

已经验证：

- 可以自动保存 PDF。
- 可以使用指定的保存目录。
- 不需要手动输入文件名。
- 文件名包含时间和任务 ID。
- 不会自动覆盖已有文件。

实际生成的文件示例：

```text
2026-11-05_16-17-26_1FD3F68B_文档1.pdf
```

因此，打印入口已经建立，后续不需要重新开发这一部分。

### 4.2 PySide6：负责桌面界面

PySide6 是 Qt 在 Python 中的绑定。

SmartPrint 的主界面使用 PySide6 开发。

主要负责：

- 任务列表。
- 任务详情。
- PDF 预览。
- 打印进度。
- 用户确认。
- 翻面提示。
- 异常处理。
- 设置和日志查看。

第一版不需要追求特别漂亮的界面。

应该优先保证任务状态清楚、打印进度清楚、当前需要用户做什么清楚，以及出现异常时能够明确提示用户。

### 4.3 PyMuPDF：负责 PDF 处理

PyMuPDF 是 PDF 文件处理库。

SmartPrint 需要通过它完成：

- 打开 PDF。
- 读取页数。
- 读取页面尺寸。
- 判断页面大小和方向。
- 生成页面缩略图。
- 按指定页码提取页面。
- 生成单页打印文件。
- 检查生成文件是否有效。

例如，一份 10 页的 PDF，可以根据任务需要生成单页临时文件：

```text
page_001.pdf
page_003.pdf
page_005.pdf
```

每次只把当前需要打印的单页文件交给打印程序。

不再依赖一次性生成整个批次的正面 PDF 和反面 PDF 后批量提交。

这样可以从文件层面配合“一个页面、一次提交、一次确认”的流程。

### 4.4 SumatraPDF：负责实际打印

SmartPrint 不准备直接编写打印驱动。

实际打印时，通过 SumatraPDF 的命令行接口调用 Windows 打印系统。

主要负责：

- 指定打印机。
- 指定 PDF 文件。
- 指定页面。
- 发起打印任务。

PyMuPDF 负责准备单页 PDF，SumatraPDF 负责将它发送给指定打印机。

需要注意：

SumatraPDF 成功发起打印命令，不代表纸张已经完整输出。

因此，SumatraPDF 的进程结果和 Windows 队列状态只能作为辅助信息，不能代替用户确认。

阶段五落地后的实际调用形态（`app/printer/sumatra.py`）：

```text
SumatraPDF.exe -print-to "HP LaserJet 1020 1016811" -print-settings "1,simplex" -silent page_005.pdf
```

几点来自实际测试的经验：

- `-silent` 必须带上，否则出错时会弹出模态对话框，进程永不退出；
- 不要用 `-version` / `-help` / `-list-printers` 探测版本，它们会打开 GUI 窗口；
- 退出码只把 `0` 当成功，其他一律按失败处理并保留原始值
  （实测 3.6.1 在打印机或文件不存在时都返回 `1`，与官方文档不完全一致）；
- 打印机名称必须用 Windows 里的**完整名称**，配置名会先做一次解析
  （`HP LaserJet 1020` → `HP LaserJet 1020 1016811`）。

### 4.5 SQLite：负责保存任务和打印进度

SQLite 是一个轻量级数据库，不需要单独安装数据库服务器，适合个人电脑上的桌面应用。

SmartPrint 需要保存：

- 打印任务基本信息。
- 原始 PDF 文件路径。
- 文件页数和页面尺寸。
- 纸张设置。
- 当前批次。
- 每张物理纸的编号。
- 每张纸正反面的对应页码。
- 每一面的打印状态。
- 打印命令发送记录。
- 用户确认记录。
- 异常纸张记录。
- 补打轮次。
- 任务创建和完成时间。

后续的异常恢复必须依赖这些数据。

如果电脑重启或者 SmartPrint 意外关闭，程序应该能够知道：

- 当前正在处理哪个任务。
- 当前是第几批。
- 当前是哪张物理纸。
- 正在打印正面还是反面。
- 当前页面是否已经发送。
- 用户是否确认完整出纸。
- 是否存在尚未补打的异常纸张。

### 4.6 watchdog：负责监控新文件

PDF24 自动保存完成后，SmartPrint 需要知道有新文件进入 `incoming` 目录。

目前使用 watchdog 监控目录变化。

但不能简单地认为只要发现一个 PDF 文件，就立即开始读取。

因为文件刚刚创建时，PDF24 可能还没有写入完成。

因此需要进行文件稳定性检查：

1. 发现新 PDF。
2. 等待文件写入完成。
3. 检查文件大小和修改时间是否持续稳定。
4. 尝试打开 PDF。
5. 确认文件有效。
6. 将文件正式登记为打印任务。

另外，目录监控只是发现新任务的一种方式。

程序启动时还需要扫描一次待处理目录，防止 SmartPrint 关闭期间产生的 PDF 没有被发现。

程序运行期间也需要定时复查目录，避免 watchdog 在极端情况下漏掉事件。

## 六、打印流程设计：以物理纸张为管理单位

这是 SmartPrint 后续开发中最重要的部分。

之前的设计主要围绕正面 PDF 和反面 PDF 进行分批处理，但经过进一步考虑，发现这种方式不能很好地处理卡纸、污损和补打问题。

因此，后续需要把打印流程改为：

**以物理纸张为管理单位，以纸张的正反两面为两个关联的打印页面。**

### 6.1 建立物理纸张与 PDF 页码的对应关系

假设原始 PDF 有 10 页。

SmartPrint 应该建立 5 张物理纸的记录：

| 纸张编号 | 正面页码 | 反面页码 |
|---|---:|---:|
| 1 | 1 | 2 |
| 2 | 3 | 4 |
| 3 | 5 | 6 |
| 4 | 7 | 8 |
| 5 | 9 | 10 |

这里的纸张编号是 SmartPrint 内部的逻辑编号，用于管理纸张：正面按这个编号升序打印，反面按这个编号降序打印（见 2.4 节反面逆序说明）。

每张纸需要分别记录正面和反面的状态。

例如：

```text
纸张 1
    正面：第 1 页
    反面：第 2 页

纸张 2
    正面：第 3 页
    反面：第 4 页

纸张 3
    正面：第 5 页
    反面：第 6 页
```

这样发生异常时，程序才能准确知道一张纸的两个页面之间是什么关系。

### 6.2 每次只提交一个页面

以第一批 5 张纸为例。

正面打印顺序：

```text
第 1 页
第 3 页
第 5 页
第 7 页
第 9 页
```

但程序不能一次性提交这 5 个页面。

正确流程是：

```text
纸张 1 正面
    |
    v
提交第 1 页
    |
    v
用户检查并确认
    |
    v
纸张 2 正面
    |
    v
提交第 3 页
    |
    v
用户检查并确认
    |
    v
纸张 3 正面
    |
    v
提交第 5 页
    |
    v
用户检查并确认
    |
    v
纸张 4 正面
    |
    v
提交第 7 页
    |
    v
用户检查并确认
    |
    v
纸张 5 正面
    |
    v
提交第 9 页
    |
    v
用户检查并确认
```

所有正面完成后，SmartPrint 提示用户整理纸张。

### 6.3 翻面确认

用户需要：

1. 检查所有正面是否完整。
2. 取出打印好的纸张。
3. 按照软件提示整理纸张。
4. 根据实际测试确定的方向重新放入进纸托盘。
5. 在软件中确认已经完成翻面。

用户没有确认之前，软件不能开始反面打印。

纸张翻面方向必须通过实际测试确定。

不同打印机的进纸方向、出纸方向和纸张重新放置方式可能不同，因此需要通过少量测试页确定：

- 哪一面朝上。
- 哪一条边先进入打印机。
- 是否需要旋转纸张。
- 反面顺序是否与翻面后的纸堆一致（每批按纸张编号降序，详见 2.4 节）。

在实际测试通过之前，不应该假设所有打印机都使用同一种翻面方式。

### 6.4 逐页打印反面

确认翻面之后，开始打印反面。反面必须按物理纸张编号**降序**提交——最后打印的正面那张纸落在出纸托盘最上方，翻面放回后它最先进入打印机：

```text
第 10 页（第 5 张纸的背面）
第 8 页（第 4 张纸的背面）
第 6 页（第 3 张纸的背面）
第 4 页（第 2 张纸的背面）
第 2 页（第 1 张纸的背面）
```

每次仍然只提交一个页面。

每一面都必须等待用户确认完整出纸。

全部完成后，第一批 5 张纸才算完成。

之后再进入下一批。

### 6.5 最后一批的处理

例如，一份 37 页 PDF，每批管理 5 张纸。

前六批分别管理 5 张纸，第七批只需要管理 2 张纸。

最后一批对应：

```text
正面：第 31、33、35、37 页
反面：第 36、34、32 页（按纸张编号降序）
```

实际上最后一批需要 4 张物理纸。

其中最后一张纸只有正面有内容，反面不需要打印。

SmartPrint 应该根据总页数自动计算纸张数量和页面对应关系，不需要用户手动计算，也不应该为了凑成双面而凭空增加页面。

## 七、异常处理与补打：以整张物理纸为单位

异常恢复是 SmartPrint 区别于普通打印软件的地方。

如果只是记录当前打印到了第几页，发生卡纸后依然很难正确恢复。

因为一张纸的正反两面是关联的。

**只要其中一面出现异常，这张物理纸就应该整体作废，正反两面都进入待补打清单。**

### 7.1 为什么必须以整张纸为单位？

假设纸张 3：

```text
正面：第 5 页
反面：第 6 页
```

如果正面第 5 页打印时发生卡纸，导致纸张损坏，那么即使反面第 6 页还没有打印，也不能继续把这张纸当作正常纸张使用。

因为后续打印第 6 页时，已经没有一张状态可靠、正面正常的纸可以使用。

同样，如果正面第 5 页已经打印成功，但反面第 6 页发生卡纸或污损，那么整张纸仍然应该作废。

不能只补打第 6 页，而把已经打印成功的第 5 页保留为最终结果。

因此，异常处理规则必须是：

- 正面异常：整张纸作废，正反两面都需要补打。
- 反面异常：整张纸作废，正反两面都需要补打。
- 无论另一面是否已经成功，都不能只补打其中一面。
- 异常纸张从当前正常打印循环中移除。

### 7.2 正常打印和异常纸张分离

假设第一批有 5 张纸：

| 纸张 | 正面 | 反面 | 状态 |
|---|---|---|---|
| 1 | 第 1 页 | 第 2 页 | 正常 |
| 2 | 第 3 页 | 第 4 页 | 正常 |
| 3 | 第 5 页 | 第 6 页 | 异常 |
| 4 | 第 7 页 | 第 8 页 | 正常 |
| 5 | 第 9 页 | 第 10 页 | 正常 |

如果纸张 3 正面第 5 页打印异常，那么：

当前正常循环中，只处理纸张 1、2、4、5。

正面正常打印：

```text
第 1、3、7、9 页
```

反面正常打印（剩余纸张按编号降序，跳过异常纸张 3）：

```text
第 10、8、4、2 页
```

纸张 3 不再参与当前正常打印循环。

它的正反两面：

```text
第 5 页
第 6 页
```

统一进入待补打清单。

等当前正常纸张全部完成后，再处理异常纸张。

### 7.3 补打必须重新打印正反两面

当前正常循环完成后，SmartPrint 开始处理待补打纸张。

例如：

```text
待补打纸张：

纸张 3
正面：第 5 页
反面：第 6 页
```

补打过程仍然遵守逐页提交、逐页确认的原则：

```text
提交第 5 页
    |
    v
等待用户确认
    |
    v
提交第 6 页
    |
    v
等待用户确认
    |
    v
纸张 3 补打完成
```

只有正反两面都经过用户确认，这张纸才算补打完成。

### 7.4 补打过程中再次发生异常

如果补打过程中再次发生卡纸，也不能直接跳过。

例如，纸张 3 在补打第 6 页时再次发生异常。

那么：

- 当前补打纸张 3 再次作废。
- 第 5 页和第 6 页重新进入下一轮待补打清单。
- 当前补打循环继续处理其他正常纸张。
- 本轮结束后，再次处理这张异常纸张。

流程如下：

```text
正常打印循环
      |
      v
发现异常纸张
      |
      v
将整张纸移入待补打清单
      |
      v
完成当前正常打印循环
      |
      v
开始补打循环
      |
      v
补打过程中再次异常？
      |
      +------ 是 ------+
      |                |
      v                |
整张纸再次作废          |
      |                |
      v                |
进入下一轮待补打清单     |
      |                |
      +----------------+
      |
      v
当前补打循环完成
      |
      v
处理下一轮待补打清单
      |
      v
所有纸张完成
```

这样可以保证每一张最终使用的物理纸，都有完整的正反两面。

### 7.5 用户如何报告异常？

第一版不需要自动识别卡纸或者纸张污损。

用户实际检查纸张后，可以点击：

- 打印正常：当前页面完整出纸。
- 打印异常：当前纸张需要作废。
- 暂停任务：暂时停止后续打印。
- 取消任务：结束当前打印任务。

点击“打印异常”后，软件应要求用户确认已经检查打印机，并取出或处理异常纸张。

随后将整张纸加入待补打清单。

不能让用户误以为点击异常按钮后，软件就能自动判断打印机内部还有多少纸张。

### 7.6 异常处理必须保留记录

每次异常都需要记录：

- 任务编号。
- 物理纸张编号。
- 正面页码。
- 反面页码。
- 异常发生在哪一面。
- 异常发生时间。
- 当前属于第几轮打印或补打。
- 用户选择的处理方式。
- 后续补打结果。

这样即使多次发生异常，也能追踪每张纸的处理过程。

## 八、任务持久化与意外退出恢复

打印任务可能已经消耗了纸张和时间。

因此，SmartPrint 必须优先保证数据安全。

不能因为程序关闭或者电脑重启，就丢失当前进度。

### 8.1 关键操作必须写入数据库

至少包括：

- 任务创建。
- PDF 接收。
- 打印参数确认。
- 当前批次开始。
- 页面打印命令发送。
- 用户确认完整出纸。
- 用户报告异常。
- 纸张进入待补打清单。
- 补打开始和结束。
- 翻面确认。
- 暂停和恢复。
- 任务取消。
- 任务完成。

### 8.2 不确定的页面不能自动重打

例如：

SmartPrint 已经向 Windows 打印系统提交第 5 页，但程序突然关闭。

重新启动后，程序无法仅凭数据库或者 Windows 队列判断第 5 页是否已经完整出纸。

因此，不能自动重新提交第 5 页。

正确的做法是：

```text
发现存在未确认的页面
        |
        v
进入待核对状态
        |
        v
提示用户检查打印机和实际纸张
        |
        v
用户确认完整出纸？
        |
        +---- 是 ----> 记录确认，继续下一页
        |
        +---- 否 ----> 按异常纸张规则处理
```

这条规则可以避免程序重启后重复打印。

### 8.3 程序恢复时应该显示明确状态

例如：

```text
任务：学习资料.pdf

当前批次：第 1 批

当前纸张：第 3 张

当前页面：第 5 页

当前阶段：等待用户核对

下一步：检查打印机和纸张，确认当前页面是否完整出纸
```

程序恢复后，不应该直接从头打印，也不能在没有用户确认的情况下自动推进。

### 阶段 4：实现 PDF 页面处理

<badge color="success">已完成</badge>

目标：让 SmartPrint 能够根据物理纸张关系，正确生成每一次需要打印的单页 PDF。

计划完成：

1. 读取原始 PDF 的全部页面。
2. 读取每一页的页面尺寸。

6. 按每批纸张数（默认 5 张，设置里可改）进行分组。

8. 处理最后一张只有正面内容的情况。
9. 保留原始 PDF，不直接修改源文件。
10. 检查生成的单页 PDF 是否有效。

例如，10 页 PDF 应该得到：

```text
纸张 1：正面 1，反面 2
纸张 2：正面 3，反面 4
纸张 3：正面 5，反面 6
纸张 4：正面 7，反面 8
纸张 5：正面 9，反面 10
```

验收标准：

使用 1、2、3、9、10、11、37 页等不同页数的测试文件，检查：

- 纸张数量是否正确。
- 正反面页码是否正确。
- 每批纸张数量是否正确。
- 最后一批是否正确处理。
- 单页 PDF 内容是否与原始页面一致。
- 不同页面尺寸是否得到正确处理。

本阶段完成后，应该能够在不连接打印机的情况下，独立验证所有页面计算逻辑。

主要实现内容：

**页面计算**

`app/core/page_planner.py` 只做纯逻辑计算，不读写 PDF，因此可以脱离界面单独验证。

- `plan_pages(page_count, sheets_per_batch, front_order, back_order)` 生成完整的打印计划。
- 正面页码按奇数升序：1、3、5、7、9。
- 背面页码按物理纸张编号降序（每批内部）：10、8、6、4、2（见 2.4 节反面逆序说明）。
- 纸张数量为 `(页数 + 1) // 2`。
- 每批张数默认为 5，可以调整。
- 最后一张纸没有背面内容时，背面页码为「无」，不会凭空增加页面。
- 计划中包含每一个物理纸张的编号、所属批次、正面页码和反面页码。
- 计划还会展开成「打印顺序」：一次提交一行，每行对应一个页面。

单页文件名由页码决定：

```text
page_001.pdf   第 1 页
page_003.pdf   第 3 页
page_037.pdf   第 37 页
```

`app/core/pdf_splitter.py` 负责所有与 PDF 文件本身打交道的操作：

- 读取全部页面，记录每一页的尺寸、旋转、文字数量和图片数量。
- 识别空白页、混合页面尺寸和旋转页面，并给出提示。
- 按指定页码提取页面，生成只有一页的 PDF。
- 生成时先写临时文件，成功后原子替换，避免留下半个文件。
- 提取后逐页比对尺寸、旋转和文字内容，确认与原页面一致。
- 源文件只读，不会被修改。

**单页文件管理**

`app/services/page_jobs.py` 负责把计划变成真实文件：

- 在 `Data/jobs/<任务号>/` 下保存一份 `original.pdf` 副本。
- 为每一页生成一个单页 PDF，文件名按页码命名。
- 同时写入 `plan.json`，记录页数、批次、每个单页文件和源文件校验值。
- 重新生成时先清理上一次的单页文件，页数变少不会留下多余文件。
- 生成前后比对源文件 SHA-256，生成过程中源文件被改动就中止。
- 提供 `ensure_page_file()`，后续阶段可以按页码单独取用某一页。

```text
Data/jobs/SP-20261105-202216-1FBD/

├── page_001.pdf
├── page_002.pdf
├── ...
├── page_037.pdf
└── plan.json
```

验收标准：

主要实现内容：

**打印机枚举与目标解析**

`app/printer/windows_printers.py` 直接调用 Windows 打印子系统的 Win32 API
（`EnumPrinters` / `GetDefaultPrinter` / `OpenPrinter` / `EnumJobs`），而不是
`Get-Printer` 或 `wmic`：

- 本项目运行环境里 `Get-Printer` 会直接返回「拒绝访问」（WMI 不可用），
  `wmic` 在新版 Windows 上已被移除，两者都不能作为唯一手段；
- `EnumPrinters` 只需要普通用户权限，返回名称、端口、驱动、状态、队列长度；
- 所有 API 都做了平台守卫，非 Windows 上调用会得到明确结论而不是让程序崩掉。

虚拟打印机（PDF24、Microsoft Print to PDF、Microsoft XPS Document Writer、
OneNote、Fax、Wondershare PDFelement、WPS PDF 等）按「名称 / 端口 / 驱动」
任一命中即可识别：

```text
名称命中：pdf24、microsoft print to pdf、onenote、fax、wondershare、kingsoft …
端口命中：portprompt:、nul:、shrfax:、\\.\pipe\、kingsoft …
```

**为什么必须做名称解析**

配置里写的是 `HP LaserJet 1020`，但系统里的完整名称是：

```text
HP LaserJet 1020 1016811
```

直接把配置名交给 SumatraPDF 会得到「打印机不存在」。因此
`resolve_printer_name()` 按「完全相同 → 忽略空格 → 打印机名以配置名开头 →
配置名包含打印机名 → 驱动名相同」的顺序匹配，并默认排除虚拟打印机。
匹配失败时返回空，**绝不会随便挑一台打印机**。

**打印队列观察**

`enum_jobs()` 读取指定打印机当前的队列，得到作业号、文档名、用户、状态位、
页数、已打印页数与排队位置。这些信息只用于：

- 发送前提醒「队列里已有 N 个作业」「有异常作业」；
- 发送后识别新出现的作业号；
- 事后回放「当时队列是什么样」。

**它永远不是「纸张已出」的依据**（readme 3.1、3.3、10.3）。

**SumatraPDF 调用**

`app/printer/sumatra.py` 负责定位、拼命令行与执行：

- 定位顺序：`config.json` 的 `printer.sumatra_path` → `drivers/SumatraPDF/`
  → 常见安装目录（含 `D:\Program\SumatraPDF`）→ 环境变量目录 → 注册表
  `InstallLocation` / `DisplayIcon` → `PATH`；
- 版本号从 Windows 文件版本信息读取，**不启动进程**——实测
  `SumatraPDF.exe -version`、`-help`、`-list-printers` 在 3.6.1 上会打开
  GUI 窗口并一直运行，无法用于探测；
- 命令行固定形态：

  ```text
  SumatraPDF.exe -print-to "HP LaserJet 1020 1016811" -print-settings "1,simplex" -silent page_005.pdf
  ```

  `-silent` 是必需的：不带的话出错会弹出模态对话框，进程永不退出；
- 退出码只认 `0` 为成功。官方 3.7 文档写的是 0/2/3/4/5/6，但实测 3.6.1 在
  「打印机不存在」「文件不存在」时都返回 `1`，因此这里不做臆测，只把非 0
  一律记为失败并原样保留退出码与输出。

**打印服务**

`app/services/print_service.py` 把上述组件串成一条可审计的流程：

```text
预检（打印机 / 虚拟打印机排除 / 页码 / 源文件 / SumatraPDF / 队列）
    |
    v
按需生成单页 PDF（复用阶段四的 ensure_page_file）
    |
    v
先记「命令即将发出」→ 启动 SumatraPDF → 等待退出
    |
    v
记录退出码、耗时、提交前后的队列快照、新作业号
    |
    v
写 task_events（print / print_blocked / print_dry_run）
```

四条不可越过的边界：

1. **绝不把页面发给虚拟打印机。** PDF24 是输入设备，发给它只会得到另一份 PDF。
2. **绝不自动重试。** 命令发出后无法知道纸上印了什么，自动重发可能重复打印。
3. **绝不把系统状态当作用户确认。** 退出码 0 只说明「作业交给了 Windows」；
   队列为空也不说明纸张已经完整出来。
4. **每次只提交一个页面。** 批次是纸张管理单位，不是提交单位。

预检会拦下这些情况（拦截时**完全不调用打印程序**）：

| 情况 | 处理 |
|---|---|
| 找不到目标真实打印机 | 拦截，并列出可用的真实打印机 |
| 目标被判定为虚拟打印机 | 拦截 |
| 打印机脱机 / 暂停 / 卡纸 / 缺纸 / 错误 | 拦截；可手动勾选「仍然发送」 |
| SumatraPDF 找不到 | 拦截，提示填写 `printer.sumatra_path` |
| 页码越界 | 拦截 |
| 源 PDF 丢失 | 拦截 |

**界面**

`app/ui/print_page_dialog.py` 提供「打印单页」窗口，从主窗口工具栏、
任务菜单或右键菜单（`Ctrl+J`）打开：

- 顶部：任务信息；
- 打印目标：页码（显示第几张纸、正面还是背面、对应哪个单页文件）+ 打印机下拉框
  （虚拟打印机也会列出来，但标注「虚拟打印机，不能选」且禁用）；
- 打印前检查：目标打印机、SumatraPDF 版本、队列快照、问题与提示；

### 阶段 6：实现逐面确认的手动双面打印

目标：完成 SmartPrint 最核心的打印流程。

计划完成：

1. 根据任务页数生成物理纸张清单。
2. 按每批纸张数（默认 5 张，设置里可改）进行分组。

### 阶段 7：实现异常恢复与补打

<badge color="success">已完成</badge>

目标：让打印过程中出现问题时，不必简单地从头开始。

计划完成：

- 打印机离线处理。
- Windows 打印队列异常处理。
- 当前未确认页面的待核对状态。
- 卡纸后的用户确认。
- 异常纸张管理。
- 整张物理纸作废。
- 正反两面统一进入待补打清单。
- 正常打印循环与补打循环分离。
- 多轮补打。
- 程序意外退出恢复。
- 任务取消。
- 完整打印事件记录。

核心规则：

**只要一张物理纸的任意一面出现异常，整张纸都作废，正反两面都需要重新打印。**

例如：

```text
纸张 3

正面：第 5 页
反面：第 6 页
```

如果第 5 页异常，那么第 5 页和第 6 页都进入待补打清单。

如果第 6 页异常，即使第 5 页已经成功，也要重新打印第 5 页和第 6 页。

异常纸张不能继续参与当前正常打印循环。

当前正常纸张完成后，再统一处理待补打纸张。

如果补打过程中再次发生异常，就把整张纸移入下一轮补打清单。

验收标准：

模拟以下情况：

- 正面打印异常。
- 反面打印异常。
- 打印机断开连接。
- 打印命令发送后程序退出。
- 用户确认前程序退出。
- 补打过程中再次发生异常。
- 用户取消任务。

确认任务不会丢失，不会在没有用户确认的情况下重复打印，异常纸张的正反两面不会被错误地分开处理。

什么时候必须停下来等用户确认。真实卡纸、真实缺纸、真实污损仍然要用户点「打印异常」，
软件不自己判断纸张结果，这一点与阶段五、阶段六一致。

补打让「异常」不再等于「从头再来」，但补打本身仍然逐面提交、逐面确认；
一张纸只要补打时再出问题，就再进下一轮，直到两面都确认完整出纸为止。

### 阶段 9（深化）：反面按纸堆逆序打印

**这一节是什么。** 阶段八之后发现的一个实际使用问题：HP LaserJet 1020 手动双面打印时，
正面逐张打印完成后，**最后打印的那张纸位于出纸托盘最上方**，用户取出整叠纸翻面放回进纸托盘后，
最上面那张会先被吸进打印机。原来反面按纸张编号升序提交，与纸堆的实际堆叠顺序相反，
反面的页码会印到错误的物理纸张上。

修完之后的顺序（以一批 5 张纸为例）：

```text
正面：第 1 页 → 第 3 页 → 第 5 页 → 第 7 页 → 第 9 页
用户确认已翻面
反面：第 10 页 → 第 8 页 → 第 6 页 → 第 4 页 → 第 2 页
```

完整的需求、边界与验收办法见 [SmartPrint_反面打印逆序开发文档.md](SmartPrint_反面打印逆序开发文档.md)。

**改了什么。**

- `app/core/page_planner.py`：`DEFAULT_BACK_ORDER` 由 `BACK_ORDER_ASCENDING` 改为
  `BACK_ORDER_DESCENDING`。排序本身没动——`plan_pages()` 一直是在**每个批次内部**对
  `BatchPlan.back_pages` 做 `tuple(reversed(...))`，所以改的只是默认值。
- `app/core/config.py` 的 `AppConfig.back_page_order` 默认值改为引用 `DEFAULT_BACK_ORDER`，
  `config/config.json` 与打包目录里的 `dist/SmartPrint/config/config.json` 同步写成
  `"even_descending"`。
- `app/ui/page_plan_dialog.py`：页面拆分窗口的「规则」一行原来直接显示配置键名
  （`odd_first` / `even_descending`），用户看不懂；改成按当前配置生成中文说明
  「正面：奇数页升序（1、3、5…）　背面：按纸张编号降序（10、8、6、4…，先打纸堆最上面那张纸的背面）」，
  换回升序时则显示「背面：按纸张编号升序（2、4、6、8…）」。
- `app/core/page_planner.py` 新增 `PagePlan.back_pages_in_print_order`：按实际提交顺序
  （逐批、批内降序）列出全部背面页码；原来的 `PagePlan.back_pages` 保持按纸张编号升序，
  含义不变，避免影响既有调用方。

**没改什么（这是本次需求的硬边界）。**

- 纸张编号与正反面页码的映射不变：第 5 张纸仍然是「正面第 9 页、背面第 10 页」。
- 批次划分、每批纸张数、正面打印顺序（奇数页升序）不变。
- 单页 PDF 的文件名与内容不变；逆序改的是**提交顺序**，不是文档内容。
- 逐面提交、逐面确认、整张纸作废、多轮补打、暂停/恢复/取消、重启后恢复、日志记录都不变。
- 数据库结构不变，没有新增字段、没有迁移；已经存在的双面会话按库里原有的 `step_index`
  继续走，不重排、不重置、不自动重发未确认的面。
- **翻面方向**配置不动。它管的是纸张怎么转、哪面朝上、哪条边先进纸；反面顺序管的是先提交
  哪张纸，两者是两件事。如果出现「顺序对了但字是倒的」，应该调翻面方向，而不是改逆序逻辑。
- 第一版不提供「反面升序/降序」设置项；`even_ascending` 只作为代码里保留的能力
  （旧配置值仍然合法），界面上不暴露开关。

**边界情况怎么处理。**

- **按批分别逆序，不跨批次全局倒序。** 12 张纸 3 批时是 5、4、3、2、1 / 10、9…6 / 12、11，
  而不是把 12 张纸的背面整体从大到小排一遍。
- **没有反面的纸张直接跳过。** 9 页 PDF 的第 5 张纸只有正面，背面顺序是 8、6、4、2，
  不生成空白背面、也不把第 9 页当背面。
- **异常纸张先排除再排序。** 第 3 张纸正面报异常后，正常反面循环是 10、8、4、2，
  第 5、6 页随整张纸进入补打清单；反面阶段才报异常时同理（纸张 4 的第 8 页异常 →
  第 7、8 页一起作废 → 剩余仍按降序继续）。
- **补打轮不需要逆序。** 本项目补打是「一次只取这一张纸」：正面打完、单独翻这一张、再打背面，
  只有一张纸时没有堆叠顺序问题，所以补打沿用原来的顺序。如果以后补打改成一摞纸统一翻面，
  才需要按同样的规则对该组纸张降序。

## 十、开发过程中必须遵守的原则

### 10.1 不要一开始就写完整软件

先完成一个最小功能，再逐步增加。

例如：

第一步只需要让窗口打开。

第二步只需要接收 PDF。

第三步只需要显示任务列表。

后续再逐步实现页面处理、真实打印、双面流程和异常恢复。

不要同时开发 PDF 页面拆分、打印控制和异常补打。

否则出了问题，很难知道是哪一个模块导致的。

### 10.2 先保证数据安全，再考虑界面美观

打印任务可能已经消耗了纸张和时间。

所以任务记录不能随意丢失。

所有关键操作都应该有记录，尤其是：

- 任务创建。
- 打印命令发送。
- 用户确认。
- 批次切换。
- 翻面确认。
- 异常发生。
- 纸张作废。
- 补打操作。
- 恢复操作。
- 任务完成。

### 10.3 不要把发送成功当作打印完成

这是整个项目最重要的技术边界。

Windows 打印队列只能提供有限的信息。

对于 HP LaserJet 1020，SmartPrint 无法可靠判断每一张纸是否完整出纸。

因此，必须明确区分打印命令已发送、Windows 打印队列已处理和用户确认纸张完整出纸。

只有用户确认，才能推进到下一页。

### 10.4 不要把批次当成批量提交单位

每批 5 张纸（默认值，设置里可改成 1–20 张），只是方便用户整理和翻面的管理单位。

它不是一次性提交一整批页面的理由。

任何时候都只能存在一个尚未经过用户确认的页面打印任务。

### 10.5 异常必须以物理纸张为单位处理

一张纸的正反两面是关联的。

不能只补打一面，也不能把已经打印成功的一面单独保留为最终结果。

只要其中一面异常，整张纸就进入待补打清单。

### 10.6 每个阶段都要有明确的验收标准

不能只看程序有没有报错。

例如，PDF 页面拆分功能即使运行成功，也不代表页码顺序正确。

必须通过测试文件逐页检查。

每完成一个阶段，都应该保存一份可运行的版本，避免后续开发破坏已经完成的功能。

### 10.7 第一版不要过早增加复杂功能

第一版只解决最核心的问题：

**接收 PDF、管理任务、页面处理、按批分纸（默认每批 5 张）、逐面确认、手动双面打印和异常补打。**

暂时不考虑：

- 网络打印服务器。
- 手机端控制。
- 云端同步。
- OCR。
- PDF 编辑器。
- 多打印机复杂调度。
- 自动识别每张纸是否完整出纸。
- 复杂的打印任务优先级系统。

这些都不是第一版必须解决的问题。

## 十一、第一版最终使用流程

理想情况下，SmartPrint 的使用流程应该是：

1. 在 Word、浏览器或者 PDF 阅读器中按下 `Ctrl + P`。
2. 选择 PDF24 虚拟打印机。
3. PDF24 自动保存 PDF 文件。
4. SmartPrint 自动接收文件。
5. 在任务列表中选择需要打印的文档。
6. 预览并确认打印设置。
7. 软件自动计算物理纸张数量和正反面页码。
8. 按照每批纸张数（默认 5 张，设置里可改）进行管理。
9. 每次只提交一个页面。
10. 用户检查实际纸张并确认完整出纸。
11. 当前批次正面完成后，提示用户整理纸张并翻面。
12. 用户确认翻面后，按纸张编号降序（先打纸堆最上面那张纸的背面）逐张打印反面。
13. 如果发生卡纸或污损，将整张异常纸张移入待补打清单。
14. 当前正常循环完成后，统一补打异常纸张的正反两面。
15. 如果补打再次异常，则进入下一轮补打。
16. 所有纸张正反两面均完成并经过用户确认后，任务才算完成。

整个过程中，用户不需要自己计算奇偶页，不需要手动拆分 PDF，也不需要记住当前打印到了哪一批。

更重要的是，即使打印过程中发生异常，也能根据已经记录的纸张状态进行处理，而不是简单地从头重新打印。

## 十三、总结

SmartPrint 是一个从实际使用问题出发的小型个人软件项目。

它不追求替代专业打印管理系统，也不打算开发一个功能庞大的 PDF 工具。

它只想把一件原本需要人工反复操作的事情做好：

**让手动双面打印变得有流程、有记录、可暂停、可恢复，并且在发生异常时能够正确补打。**

整个项目采用 Python + PySide6 + PyMuPDF + SQLite 的技术组合，利用 PDF24 作为统一打印入口，再通过 SumatraPDF 调用 Windows 打印系统。

开发过程中坚持分阶段完成，每一个阶段都有明确的目标和验收标准。

目前已经完成 PDF24 虚拟打印入口、Python 程序框架、PDF 自动接收和任务管理界面。

页面计算和单页 PDF 生成也已经完成，并且已经能把指定的一页真正交给 HP LaserJet 1020，
同时留下命令、退出码与队列记录。

逐面确认的手动双面打印和异常恢复、多轮补打也已经在离屏环境中通过自动化验收；
背面按纸张编号降序提交（先打纸堆最上面那张纸的背面）这条规则也已经并入计划生成、
界面显示与整个提交顺序。

阶段八把这套流程收口成可以直接使用的软件：界面补上了纸张示意图、翻面提示、设置窗口、
日志查看和异常总览，数据可以备份、可以归档，最后用 PyInstaller 打包成
`dist/SmartPrint/SmartPrint.exe`——把整个目录拷到没有 Python 的 Windows 机器上双击就能用，
配置、日志和打印记录都落在 exe 同级的 config/、logs/、Data/ 里。

从阶段二到阶段八，每个阶段都有对应的自动化验收脚本（`tools/verify_stage*.py`），
一共八百多项检查，用来确保后面加功能时不会把前面的能力改坏。

这不是一个追求功能数量的软件项目。

我更希望它能够解决一个真实存在的问题：打印几十页学习资料时，不必再反复计算页码、担心卡纸后漏页，也不必因为一次打印异常就从头开始。

**一个功能一个功能地完成，最终把 SmartPrint 做成真正能在日常生活中使用的软件。**
